## Findings

### SA-2026-10-14-01 · Low · Servers received secrets their mode never uses
- **Where:** `deploy/ansible/roles/cipheroom/tasks/main.yml` (environment file), `tasks/env.yml`.
- **Evidence:** `deploy/.env` holds the keys of every mode and all of them were written to every server: the
  LiveKit-mode servers held Cloudflare's SFU app secret, TURN API token and analytics token (and the beta also the
  Cloudflare DNS token), none of which the api reads in that mode (names checked on the server, values never printed).
- **Impact:** a compromise of the server's `.env` (root-only, 600) would also hand out credentials for another
  deployment's provider. Several of these were already revoked, which limited the impact.
- **Fix:** the environment file now leaves out what the mode never reads: Cloudflare SFU/TURN/DNS keys in LiveKit
  mode, Cloudflare analytics when Hetzner traffic is the usage source, the tunnel token in direct mode. The DNS token
  still reaches certbot's own root-only credentials file.
- **Status:** fixed (`Fix SA-2026-10-14-01` commit); live on `cipheroom-direct` (its `.env` has no Cloudflare or
  tunnel keys), on the beta with its next `scripts/deploy.sh`.

### SA-2026-10-14-02 · Medium · LiveKit on the host network can reach the isolated telemetry services
- **Where:** `deploy/docker-compose.yml` (`livekit`: `network_mode: host`, runs as root with `NET_BIND_SERVICE`).
- **Evidence:** from the host's network namespace, which LiveKit now shares, Prometheus, Loki, Tempo, Grafana,
  cadvisor and the api answer on their Docker addresses. The 2026-10-11 audit had put the telemetry services on internal
  networks so that nothing internet-facing could reach them.
- **Impact:** an attacker who first gains code execution inside LiveKit (internet-facing) could query the telemetry
  backends, which have no authentication of their own: pseudonymous call metadata, 7 days. No keys, media, chat or files
  are there. LiveKit's own TURN refuses private and loopback peers, so call participants can't use the relay for this.
- **Fix:** LiveKit no longer terminates TLS anywhere: `edge` terminates TURN over TLS in both TURN modes (direct, and a
  TURN domain in tunnel mode), so LiveKit needs neither port 443 nor a certificate. It runs as uid 10002 with no
  capabilities, and ufw rejects new connections from that uid to 172.16.0.0/12, 10.0.0.0/8 and 192.168.0.0/16 (replies
  to connections the api and edge open still pass). Host networking itself stays: it is what makes the TURN relay work.
  Verified on `cipheroom-direct`: uid 10002 gets no connection to Prometheus while another uid does; forced TURN over
  TLS and over UDP and a mixed Chromium + WebKit call pass.
- **Status:** fixed (`Fix SA-2026-10-14-02, -03` commit); live on `cipheroom-direct`, on the beta with its next deploy.

### SA-2026-10-14-03 · Low · The certbot image is outside Dependabot
- **Where:** `deploy/ansible/group_vars/all.yml` (`certs_certbot_image`), `scripts/ip-cert.sh` (`CERTBOT_IMAGE`).
- **Evidence:** both pin a version tag in places Dependabot doesn't read. With short-lived IP certificates, certbot now
  runs every 12 hours as root with network access.
- **Impact:** a vulnerable certbot would stay in use until someone notices.
- **Fix:** certbot is now the compose services `certbot` and `certbot-dns` (profile `certs`, pinned by digest) in
  `deploy/docker-compose.yml`, which Dependabot reads; the certs role and `ip-cert.sh` use `docker compose run`.
  Verified: a renewal run on `cipheroom-direct` succeeds through the new service.
- **Status:** fixed (`Fix SA-2026-10-14-02, -03` commit).

### SA-2026-10-14-04 · Low · Dependency updates merge without tests
- **Where:** `.github/` (Dependabot, no test workflow).
- **Evidence:** three Dependabot merges on 2026-10-14 broke things: TypeScript 7 (#34) stopped every web image build
  (which also blocked deploying the CVE-2026-70159 fix), and Tempo 3 (#35) crash-looped on the beta.
- **Impact:** security patches can be blocked by an unrelated broken update, and breakage reaches servers unnoticed.
- **Fix:** `.github/workflows/ci.yml` runs the backend and web tests, `scripts/lint.sh` and both production image builds
  on every pull request and push to main (read-only, actions pinned by SHA). `lint.sh` now has Tempo, Loki, the
  collector and Prometheus check our config with the image versions pinned in compose (Tempo's verifier rejects the
  old `compactor` config). Dependabot ignores TypeScript majors (#39).
- **Status:** fixed (`Fix SA-2026-10-14-04` commit); active once the workflow is on `main`.

### SA-2026-10-14-05 · Info · Reboot pending since first boot
- **Where:** server `cipheroom-direct`.
- **Evidence:** `/var/run/reboot-required` since 20:00 UTC (kernel, libc from the first-boot upgrade).
- **Status:** accepted — the configured automatic reboot applies it at 04:30 UTC.

### SA-2026-10-14-06 · Info · Direct-mode design trade-offs
- Firefox ignores TURN over TLS to an IP address, so on networks that allow only HTTPS it can't connect (it still uses
  direct UDP/TCP and TURN over UDP elsewhere).
- An HTTPS client that offers no ALPN reaches TURN, not the site (Ansible's `uri` module, some scanners).
- The IP certificate is listed in Certificate Transparency logs.
- **Status:** accepted and documented (`docs/deployment-hetzner.md`, design doc).

### SA-2026-10-14-07 · Info · Certificate directory shows group `lxd`
- **Where:** `/etc/cipheroom`, `/etc/cipheroom/tls` (group 101 so edge's nginx can read the certificate).
- **Evidence:** gid 101 is `lxd` on Ubuntu; the group has no members.
- **Status:** accepted (cosmetic; documented in the certs role).

### SA-2026-10-14-08 · Info · Internet-facing containers have no memory limits
- **Where:** `edge`, `web`, `api`, `livekit` (the telemetry services have limits).
- **Impact:** a flood that makes one of them grow could starve the others on a 4 GB server; edge's connection and
  request limits make this unlikely.
- **Status:** accepted for now; revisit with load numbers.

## Checked and passed
**A. E2EE invariant**
- No changes to `web/src` or `src` since the previous audit apart from dependency updates and the api Dockerfile.
- No key/secret logging, `location.hash`, `innerHTML` or `bypassSecurityTrust*` in the app (spot checks repeated).
- The edge proxy terminates TLS and passes HTTP and TURN only; TURN carries SRTP with our frame encryption inside.

**B. Backend**
- `AllowedHosts` on the direct server: the server's IP and localhost only; a foreign `Host` gets 400.
- The api's health and metrics endpoints aren't reachable from outside (`/api/health` 404; `/metrics`, `/health/*`
  return the app's fallback page).
- LiveKit API keys come from the environment; the api reaches LiveKit's API on 172.30.0.1, which isn't routable from
  outside.

**C. Frontend**
- CSP, Referrer-Policy, Permissions-Policy, nosniff and HSTS arrive unchanged through edge (`security-check.sh`).

**D. Supply chain**
- `scripts/security-check.sh`: no secrets in tracked files; `deploy/.env`, `.env.hetzner`, `.env.hetzner.direct`
  ignored and 600; new per-server state, tfvars, inventory and known_hosts files ignored; NuGet and npm audits clean.
- Dockerfile bases pinned by digest (now ASP.NET Core 10.0.13); the new edge image pinned by digest; compose images by
  exact version; workflow actions by commit SHA; Ansible collections exact.

**E. Deploy configuration**
- edge: TLS 1.2 and 1.3 only (cipher strength A), session tickets off, per-address connection and request limits, 1 MB
  bodies, `server_tokens off`, no access log. Client-address headers are always overwritten; a PROXY header sent from
  outside is rejected (only the internal sockets accept it).
- Port 80 serves only the ACME check (read-only webroot) and redirects everything else.
- Certificates: Let's Encrypt key 600 root; edge's copy 640 root:101 in a 750 directory; renewal timer every 12 h;
  expiry on the host dashboard and in `deploy.sh`.
- Terraform: 80/443 plus LiveKit's ports in direct mode; SSH from the operator only; the Primary IP has delete
  protection.
- Ansible: secrets only in `no_log` tasks; per-server host-key pinning kept for named servers (`deploy.sh` passes
  `StrictHostKeyChecking=yes` with that server's file).
- LiveKit: API (7880) bound to loopback and 172.30.0.1 only; ufw allows 7880/5349 only from 172.30.0.0/24; LiveKit's
  TURN denies private/loopback peers and relays only to the node's media ports; media limited to the public IP.
- All containers: `cap_drop: ALL` and `no-new-privileges` except cadvisor (accepted 2026-10-11); LiveKit adds only
  `NET_BIND_SERVICE`.

**F. Live server**
- Ubuntu 26.04.1 LTS, no security updates outstanding, automatic reboot at 04:30.
- sshd: no root, keys only, `AllowUsers cipheroom`, no forwarding, MaxAuthTries 3, post-quantum KEX first.
- Only `cipheroom` as a login user, in `sudo` only; `docker` and `lxd` groups empty; Docker socket root:docker 660.
- fail2ban active for sshd; Docker log rotation; `.env` 600 root.
- ufw: default deny in; 22, 443 and LiveKit's public ports; 7880/5349 from the LiveKit bridge only.
- Listening sockets match: sshd, edge (80/443 via docker-proxy), LiveKit's media and TURN ports, LiveKit's API on
  172.30.0.1.
- Outside view (TCP, from the operator's machine): of 22, 80, 443, 3000, 3478, 5349, 7443, 7880, 7881, 8080 and
  9090, only 22 (operator's IP only), 80, 443 and 7881 answer; 7880 (LiveKit API) and 5349 (TURN behind edge) are
  filtered. TLS on 443: TLS 1.2 and 1.3 only, cipher strength A (`nmap ssl-enum-ciphers`).
- `security-check.sh https://2.31.51.201`: all green, Grafana login required and rate-limited.
